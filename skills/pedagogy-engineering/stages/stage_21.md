# Stage 21: Quality Validation, Completion Criteria & Failure Conditions

Execute a rigorous, formal audit of the compiled Learning Plan before finalizing delivery.

---

## 1. The 53-Point Pedagogical Validation Checklist

Verify and confirm that every single criterion is satisfied:

### Intake Validation (1–6)
- [ ] 1. Audience is explicitly defined with demographic and prior knowledge baseline.
- [ ] 2. Topic/domain boundaries are clearly established.
- [ ] 3. Learning goal is defined and learner-centered.
- [ ] 4. Learning context and operating setting are defined.
- [ ] 5. Relevant delivery and technical constraints are defined.
- [ ] 6. User-provided facts are strictly separated from agent inferences and assumptions.

### Learning Validation (7–16)
- [ ] 7. A coherent learning problem is diagnosed (current state vs target state gap).
- [ ] 8. The primary learning goal directly addresses that problem.
- [ ] 9. Every learning objective contributes directly to the primary goal.
- [ ] 10. Every objective uses an observable and measurable action verb (no vague verbs).
- [ ] 11. Every objective has an explicit depth and complexity specification.
- [ ] 12. Knowledge and skill content directly supports the objectives.
- [ ] 13. Content scope explicitly defines core vs excluded boundaries.
- [ ] 14. Prerequisites are identified wherever necessary.
- [ ] 15. Logical dependencies between objectives are fully mapped.
- [ ] 16. Progression builds capability systematically from foundation to mastery.

### Activity Validation (17–23)
- [ ] 17. Every learning objective has at least one dedicated learning activity.
- [ ] 18. Activities require active learner cognitive or practical execution (no passive exposition).
- [ ] 19. Activities authentically exercise the target capability.
- [ ] 20. Instructional scaffolding is specified across exposure levels.
- [ ] 21. Multi-tiered feedback (explanatory, consequence, corrective) is defined.
- [ ] 22. Learner independence systematically increases as support fades.
- [ ] 23. Transfer requirements are explicitly specified (or justified as not required).

### Evidence Validation (24–27)
- [ ] 24. Every learning objective has observable, measurable evidence of achievement.
- [ ] 25. Concrete success benchmarks and criteria are established.
- [ ] 26. Realistic assessment conditions (tools, time, hints) are defined.
- [ ] 27. Evidence measures genuine pedagogical learning rather than incidental game win-states.

### Pedagogy Validation (28–32)
- [ ] 28. The pedagogical approach follows from the learning requirements.
- [ ] 29. The approach is justified.
- [ ] 30. The approach is consistent with the audience.
- [ ] 31. The approach is consistent with the learning context.
- [ ] 32. The approach is consistent with the progression.

### Learning-Experience Validation (33–38)
- [ ] 33. Required learner experiences are explicitly identified.
- [ ] 34. Each major experience requirement has a pedagogical justification.
- [ ] 35. Experience requirements support identified objectives or learning processes.
- [ ] 36. Experience requirements specify educational function rather than merely aesthetic preference.
- [ ] 37. Learner agency and challenge requirements are specified where relevant.
- [ ] 38. The experience requirements do not prematurely prescribe complete game mechanics.

### Learning-Environment Validation (39–45)
- [ ] 39. Required environmental characteristics are explicitly identified.
- [ ] 40. Each major environment requirement has a pedagogical justification.
- [ ] 41. Contextual fidelity is specified only where educationally necessary.
- [ ] 42. Required environmental interactions are identified.
- [ ] 43. Required environmental consequences or observable states are identified where relevant.
- [ ] 44. Environment requirements support objectives, activities, transfer, or pedagogical approach.
- [ ] 45. The environment specification does not become a detailed game-world design.

### Game-Handoff Validation (46–53)
- [ ] 46. Required learner interactions are explicitly identified.
- [ ] 47. Game requirements trace to pedagogical requirements.
- [ ] 48. Game form is derived from interaction requirements.
- [ ] 49. Game-form recommendation is pedagogically justified.
- [ ] 50. The document does **not** prescribe game lore, art style, characters, or game loop.
- [ ] 51. Game designer responsibilities remain clearly separated.
- [ ] 52. Open design decisions are identified.
- [ ] 53. The final handoff is sufficiently specific to guide game design.

## 2. Completion Criteria

The skill execution is considered complete **only if**:
1. All mandatory intake information is secured.
2. The learning problem statement is explicit.
3. The learning goal is learner-centered.
4. Objectives are observable and measurable.
5. Content scope is strictly bounded with explicit exclusions.
6. Cognitive depth is calibrated for every objective.
7. Progression follows logical dependencies.
8. Activities provide active practice for all objectives.
9. Scaffolding fading logic is defined.
10. Feedback provides explanatory and consequence insight.
11. Evidence isolates learning from gameplay performance.
12. Transfer requirements are addressed.
13. Pedagogical framework is defended.
14. Required learner experiences are explicit.
15. Required environmental characteristics are explicit.
16. Contextual fidelity is justified where required.
17. Game-facing learning requirements are explicit.
18. Game form is derived via the derivation chain.
19. The Traceability Matrix links all goals, LOs, activities, experiences, environments, evidence, and GDRs.
20. All major experience requirements have pedagogical justification.
21. All major environment requirements have pedagogical justification.
22. The final deliverable follows the 24-section static output schema (A through X).
23. The document is usable by a game designer without requiring the agent to perform game design.

---

## 3. Strict Failure Conditions

The skill execution is considered an **unacceptable failure** if:
* The audience was independently invented without user input.
* The learning goal is merely a topic label (e.g. "Teach fractions").
* Vague verbs (understand, learn, appreciate) are used without operationalization.
* Content is listed as an information dump without performance mapping.
* Learning activities are disconnected from objectives.
* Progression is based on arbitrary topic order rather than prerequisite dependencies.
* Evidence of learning is missing or conflated with game high-scores / winning.
* Required learner experience is unspecified where it materially affects learning.
* Required environmental characteristics are unspecified where they materially affect learning.
* Environmental realism is prescribed without pedagogical justification.
* Game mechanics are proposed without pedagogical justification.
* Genre is selected solely from the subject matter.
* The output becomes a Game Design Document (story, art style, UI design, technical engine).
* Any section of the 24-section static schema (A–X) is omitted, reordered, or renamed.
* Important assumptions are presented as user-provided facts.
* Objectives cannot be traced to evidence.
* Experience requirements cannot be traced to pedagogical requirements.
* Environment requirements cannot be traced to pedagogical requirements.
* Game requirements cannot be traced to learning requirements.

---

## 4. The Governing Question

Keep this central question at the core of all evaluation:

> **"What does the learner need to become capable of doing, how should they learn it, what should they experience, what must the learning environment enable, and what must the eventual game support in order for that learning to occur?"**
